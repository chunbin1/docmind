# DocMind RAG 评估报告

> 评估日期：2026-05-16
> 评估对象：DocMind RAG 检索-生成链路
> 测试文档：《探迹科技员工手册 v4.0》（99 chunks）

## 一、评估方法

LLM-as-Judge + 自动生成测试集，无需人工标注：

1. **测试集生成**：对文档每个 chunk 调用 LLM 自动出题（事实型 / 理解型），标注难度与答案来源 chunk
2. **跑 pipeline**：对每题走真实 RAG 流程（向量检索 top-3 → 注入 system prompt → LLM 生成答案）
3. **四维打分**：检索召回率（规则）+ 精确率 / 忠实度 / 相关性（LLM-as-Judge，GLM-4.7）
4. **数据清洗**：剔除 LLM 出的格式/元信息废题（页码、行数、"第几个数字"等）及限流失败样本

## 二、配置快照

| 项 | 值 |
|----|----|
| 分块大小 | 500 字符 |
| 块重叠 | 50 字符 |
| 检索 top-K | 3 |
| Embedding 模型 | embedding-3 |
| 答案生成模型 | glm-4-flash |
| Judge 模型 | glm-4.7 |
| 有效测试样本 | **184 题**（134 easy + 50 medium，全部有效，无失败样本）|

## 三、评估结果

### 总体指标（184 题）

| 指标 | 分数 | 含义 |
|------|------|------|
| 召回率 Context Recall | **88.0%** | 检索是否找到含答案的 chunk |
| 精确率 Context Precision | **73.7%** | 检索到的 chunk 有多少真正有用 |
| 忠实度 Faithfulness | **90.5%** | 回答是否基于检索内容、无编造 |
| 相关性 Answer Relevancy | **89.5%** | 回答是否切题、覆盖期望答案 |

### 按难度分解

| 难度 | 样本 | 召回 | 精确 | 忠实 | 相关 |
|------|------|------|------|------|------|
| easy | 134 | 87.3% | 74.5% | 89.9% | 89.6% |
| medium | 50 | 90.0% | 71.6% | 92.0% | 89.4% |

难度对指标影响不大，medium 题召回甚至略高（问题更具体，检索更精准）。

## 四、结论

**生成环节优秀，检索环节是瓶颈：**

- ✅ **忠实度 90.5%、相关性 89.5%** — 即使用 glm-4-flash 生成，回答基本不编造、切题率高
- ✅ **召回率 88%** — 检索大概率能命中答案所在的 chunk
- ⚠️ **精确率 73.7%（短板）** — top-3 中约 1/4 的 chunk 对回答无帮助，是干扰噪音

## 五、优化建议（按性价比排序）

| 优先级 | 改进 | 预期提升 | 说明 |
|--------|------|---------|------|
| 🥇 | top-K 3→8 + 加 Rerank | 精确 / 召回 +5~10% | 先粗召回再精排，性价比最高 |
| 🥈 | 按章节分块（父子 chunk / ParentDocumentRetriever）| 精确 +10~15% | 解决固定字符分块切碎语义的根因 |
| 🥉 | Query 改写 | 召回 +5~8% | 缓解用户用词与文档用词不一致 |
| 4 | 向量 + 关键词混合检索 | 召回 +5~10% | 互补盲区（术语/编号靠关键词）|

**精确率 73.7% 的根因**：当前固定 500 字符分块会把完整语义切断，导致 chunk 向量"语义模糊"，检索时混入相关性低的块。最有效的根治是按章节/段落分块 + Rerank 二次精排。

## 六、评估系统能力（本次交付）

- 测试集自动生成（LLM 出题，无需人工标注）
- 四维 LLM-as-Judge 评分（合并为单次调用，降 2/3 请求量）
- 自适应限流（慢启动 + 退避）+ 请求超时 + 失败重试
- 可续跑（保留成功结果，只补失败/未评）
- Token 用量记录（单条 + 整轮汇总）
- 结果持久化（SQLite）+ 前端面板查看（问题/答案/评分/judge 理由）

### 已知限制

- Judge 模型为 GLM-4.7，账户速率限制严格，大批量评估耗时长且易触发限流（已通过节流+重试+续跑缓解）
- 精确率算法为整组打分（粗），未做逐 chunk 加权（RAGAs 风格），属简化实现
- Token 统计仅覆盖单轮成功调用，不含跨轮重试/重启的累计消耗，不能用于精确成本核算
